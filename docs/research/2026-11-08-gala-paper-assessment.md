# GALA+ 论文研读与真实环境落地评估

研读日期：2026-11-08。目标：以工作区论文为蓝本，构建可接入真实微服务环境的智能排障系统。

本文是研读记录和可行性评估。具体环境、技术栈、验收阈值与实施范围仍需根据现有系统确定；下文工程建议均为建议，不代表已完成验证或已确定的实施设计。

## 结论

可以将 GALA+ 作为架构蓝本独立实现。最适合首先落地的能力是：接收真实告警，关联指标、日志、调用链，生成根因候选、传播路径、可核查证据及分阶段处置建议。核心价值是“统计筛选 + 拓扑约束 + 多模态证据调查”，而不只是多智能体对话。

论文及公开资料足以指导核心流程重实现，但核心源码不公开，不能承诺精确复现作者实现和数值。论文没有验证实际修复执行及其恢复效果。生产落地需要另外解决数据接入、实体关联、缺失信号、运行时预算、结果可追溯及真实事故评测。

工作区初始仅有论文 PDF，没有已有项目代码、配置或遥测样本。

## 论文的四阶段设计

### 1. 初始假设生成（第 3–4 页，§3.1）

指标侧使用 BARO 生成排序；调用链侧使用 STRIX 生成互补排序。日志暂不参与粗排，因为资源类故障可能没有错误日志。

STRIX 从 spans 构造调用方 → 被调用方的有向依赖图，聚合延迟和调用量，再计算三个维度：

- 不稳定性：`P99 / P50`，突出长尾延迟。
- 中心性：`PageRank × (1 + 入度) / (1 + 出度)`。
- 影响度：累计 span 时长乘以本服务平均延迟中扣除最慢下游平均延迟后的比例，比例截断到非负值。

三个维度各自排序后通过 Reciprocal Rank Fusion 融合，平滑常数为 60。该 RRF 用于 STRIX 内部三个维度，不能与后续跨模态融合混为一谈。

Consolidation Agent 再融合指标和 trace 排名，保留候选来源、故障假设及置信度。其置信度为模型输出，论文未证明它是经过校准的故障概率。由指标名或另一候选推测出的故障类型应保留“假设”状态。

### 2. 按 Pod 组织诊断上下文（第 4 页，§3.2）

每个调查对象的诊断包包含：事件窗口内按秒组织的指标 JSON、一跳依赖子图及边属性、按时间排序的日志。日志优先保留错误与异常，去重并控制长度；必要时补少量普通日志，以区分静默故障与没有采集到日志。

论文将指标折线图编码改为 JSON。核心是保留可分析的信息同时控制上下文大小，不要求为每个指标生成图片。

### 3. 图约束调查（第 4–5 页，§3.3、Algorithm 1）

默认并行调查前 6 个候选，阈值 θ=0.6，邻居批大小 b=2（第 7 页）。每次调查返回根因置信度、证据摘要、因果解释、支持因素和反对因素，并写入共享调查记录。

种子达到阈值则停止该分支；否则随机分批调查其直接前驱和后继。当一批中有候选达到阈值，或邻居耗尽时，该分支结束。

关键实现边界：伪代码没有递归调用邻居的 DeepDive，主动调查范围是种子及其一跳邻居。邻居自己的诊断包可以显示其一跳拓扑，但这不等同于主动递归调查更多节点。多跳搜索属于可评估的扩展。置信度提前停止也意味着存在遗漏其他原因的可能。

### 4. 证据综合与事件报告（第 5 页，§3.4）

Evidence Synthesis Agent 综合调查结果，使用初始信号约束重排，并检查最高候选能否解释其他分支的症状及反证。Remediation Agent 输出事故摘要和三类建议：立即缓解、永久修复、预防措施。

论文中的 incident response 是建议生成。没有给出执行器、生产变更结果、恢复成功率或 MTTR 实验。

## 实验支持什么

主实验使用 RCAEval RE2：Online Boutique 和 Train Ticket 各 90 个注入案例，覆盖 CPU、内存、磁盘 I/O、网络延迟、socket 错误、丢包六类故障；实验系统分别有 17 和 69 个微服务（第 6 页）。

| 主论文表 1（第 8 页） | Online Boutique | Train Ticket |
| --- | ---: | ---: |
| AC@1 | 74.44% | 73.33% |
| AC@3 | 98.89% | 85.56% |
| MRR | 0.854 | 0.801 |
| 平均单案时间 | 52.87 秒 | 63.16 秒 |
| 单案总 tokens | 32.7K | 90.4K |

这些指标仅要求命中故障 Pod，不要求故障类型正确（第 7 页，§5.2）。对最强 LLM 基线的 AC@1 优势为 26.09 / 25.55 个百分点；对两套系统各自最强非 LLM 基线的优势为 7.77 / 6.66 个百分点。不能将“提升超过 25 个百分点”泛化到所有基线。

补充报告采用 100 个 AegisLab 案例、25 类故障。作者方法的 AC@1 为 30%，AC@3 为 62%，MRR 为 0.477；Flow-of-Action 分别为 28%、52%、0.381。报告明确说 Top-1 只多命中两例，优势不显著。这是判断真实环境可用性的重要边界。补充表将方法标为 GALA，主文以此作为 GALA+ 的补充结果引用，存在命名差异，复现实验需记录具体版本。

SURE-Score 从证据支撑、操作可行性、诊断精确性和排障逻辑四个维度评价报告。人工评价结果较好，但两个模型评委对证据支撑打分差异明显（第 8–9 页）。因此文字评分不能代替根因正确性或真实处置效果评测。

上述时间及成本来自论文环境，不能直接作为目标系统的服务等级或当前 API 费用承诺。论文默认模型通过 API 调用，无需本地 GPU；本地部署模型则需要另行评估资源。

## 已核实的复用条件与歧义

1. **作者核心代码不公开。** 第 11 页与公开 README 一致。仓库提供技术报告、标注参考报告、样例输出及第三方基线，不是可以直接启动的完整 GALA+ 服务。
2. **有可用的公共数据与基线。** README 明确实验采用 RCAEval RE2；RE2-OB 和 RE2-TT 各有 90 个三模态案例，可先用于验证流程。公共基准通过后仍需在目标环境的事故数据上验证。
3. **BARO 描述与代码不一致。** 主论文 §3.1.1 将其描述为建立因果 DAG 并按影响排序；原作者资料介绍 BOCPD 与 RobustScorer，GALA 公开仓库内的 `baro()` 则按时间分割数据，对正常段拟合 RobustScaler，再按异常段最大分数排序，没有构图步骤。闭源主系统是否另有修改无法确认。工程上应明确基线版本及适配规则，不能将公开 BARO 直接标作因果图算法。
4. **服务与 Pod 粒度尚未闭合。** STRIX 节点是服务，评估目标是 Pod；真实环境中一个服务有多个副本，需要通过资源标识、部署信息和采集标签建立映射。缺少实例标识时只能报告服务级候选。
5. **调用图不等于因果图。** 论文将依赖图描述为 DAG，但聚合后的真实服务调用可能包含环。边表示调用关系，传播方向和因果解释仍需时间、指标和错误证据支持。
6. **数据处理细节不完整。** 时间窗口长度、日志预算、采样策略、零分母、无下游节点、缺失 spans、重叠子调用和完整提示词需明确。STRIX 的影响度是延迟启发式，不能直接当成精确的独占 CPU 时间。
7. **置信度与重复调查需工程化。** 共享邻居可能被多个分支调查；需要定义缓存、并发写入、冲突记录、超时、总调用预算和停止原因。缓存或去重改变随机调用次数时，应在实验配置中记录。

## 面向真实环境的建议路线

建议在“基准与历史事故回放 → 真实环境只读接入 → 在线并行观察 → 受控处置”四步推进。这样可以逐步检验输入质量、推理收益和实际使用效果。

### 第一阶段：建立可验证的诊断内核

实现数据规范化、BARO 适配、STRIX、诊断包、候选融合、一跳调查、证据综合与报告输出。先用公共数据及可获得的历史事故运行；保留普通基线与消融结果，以验证 LLM 调查是否带来收益。

推理输入必须隔离真实标签、包含故障名称的目录、参考答案及事后复盘结论，避免答案泄漏。固定数据版本、事件划分、随机种子和模型配置。

### 第二阶段：接入现有观测体系

围绕现有系统提供告警、指标、日志、traces 和实体信息的只读适配器。对于已有监控栈，优先使用现有查询接口，具体产品与语言栈在了解现场后确定。

首先解决 `service → workload → pod/container` 标识、时间与单位统一、正常基线和故障窗口、trace 采样率、缺失信号说明，以及部署/配置变更关联。变更信息是生产扩展能力，并非论文已验证模块。

使用窗口 `[τ−Δτ, τ+Δτ]` 时，在线分析只能读取已发生的数据；必须记录数据截止时间。离线回放也需要相同截止约束，不能用未来遥测夸大实时诊断能力。

### 第三阶段：在线并行观察与 SRE 反馈

接收真实告警，在现有人工排障流程旁运行并记录结果。每条结论附原始证据定位信息：时间窗口、实体、指标值、日志定位及 trace/span 标识。报告应明确数据覆盖度、反证、待查项和“证据不足”，使 SRE 能核查并纠正结论。

服务端需补充任务状态、查询限流、重试、去重、超时、审计及单次诊断成本统计。真实日志属于证据内容，不能获得执行工具或更改系统指令的能力；模型访问边界和数据外发方式按实际部署约束确定。

### 第四阶段：验证处置闭环

依据环境中的资源、运行手册和历史结果形成可执行方案，先验证前置条件和预期效果，再逐步评估受控执行。需要记录变更范围、恢复验证、失败处理和回滚，单独评估处置成功率与影响。论文的建议质量评分不能替代这一阶段。

## 建议验收维度

| 维度 | 应观察的结果 |
| --- | --- |
| 数据可用性 | 三模态覆盖率、时钟误差、实体映射正确率、采样和缺失比例 |
| 诊断正确性 | 分开统计服务命中、Pod 命中、故障类型正确率；AC@1、AC@3、MRR |
| 候选质量 | 真根因是否进入初始候选，以及后续重排是否改善结果 |
| 证据质量 | 引用可定位、数值可核验、无虚构服务、可识别反证与证据不足 |
| 运行效率 | 端到端延迟、失败率、查询负载、token 和单案成本 |
| 实际使用效果 | SRE 采纳与纠错、节省调查时间、覆盖的真实故障类别 |
| 后续处置效果 | 恢复成功率、回滚率、误操作影响与 MTTR，单独实验 |

不宜在缺少目标系统样本时承诺准确率。阈值应根据业务影响、事故基线和人工处理流程共同确定。

## 下一步需要了解的环境

最先确认实际微服务的部署方式，以及现有指标、日志、调用链和告警分别由什么系统提供。随后才能确定接入边界、数据契约和第一批试点服务。模型调用方式、数据出网限制、历史事故样本及可接受时延也会影响实现选择。
