# M0 本阶段设计方案文档：实验环境与接口验证

日期：2026-11-16。版本：0.1。状态：**方案已确认；实现和限定验证完成，交付待用户审查**。

项目仓库：`git@github.com:NotYourBug/glide-rca.git`。本阶段沿用[全局框架](../01-architecture-and-modules.md)和[推进顺序](../development-sequence.md)中的首个里程碑 M0。模块编号 M01–M10 与阶段编号 M0–M3 分别使用。

## 1. 阶段概述与目标

### 1.1 解决的问题

后续诊断依赖可运行的微服务以及可通过程序读取的指标、日志和调用链。本阶段建立并验证这些前提，交付一个固定版本、可重复启动的实验环境，以及足以支持后续适配器设计的真实接口样本。

本阶段只涉及 M02 多源适配之前的接入验证，不实现平台业务适配器。M0 读取程序是小型实验探针，后续 M1 依据样本建立正式数据契约。

### 1.2 核心交付物

1. 接入项目 Git 仓库，保留现有设计资料，明确哪些文件可以提交。
2. 固定版本的 OpenTelemetry Demo minimal 环境及本机覆盖配置。
3. 一份可按步骤启动、查询、注入指定故障、恢复和停止的操作说明。
4. 一个 Python 标准库实现的只读 HTTP 探针及小型单元测试。
5. 健康、Payment 错误和 Ad CPU 场景的接口样本、运行版本与资源记录。
6. 一份实际验证结论，明确通过、未通过和缺失数据，供用户审查。

### 1.3 方案确认前的现场事实

- 用户已说明仓库为空；本次 GitHub 元数据读取确认仓库存在，默认分支为 main，仓库大小为 0，当前可见性为 public。SSH 认证与推送尚未验证。
- 本机约 16 GB 物理内存；2026-11-16 只读检查已找到 Git、Python、Docker 和 WSL 命令。命令存在不代表 Docker Linux 引擎、Compose 或 WSL2 后端已经可用。
- 当前工作区只有论文和设计资料，没有应用工程，也尚未建立本地 Git 仓库。
- 前期选择沿用 OTel Demo 3.1.0，源提交 `dedc0178918e260823323b8d95005a8cb924b007`；本阶段继续使用该版本，不追随 latest。

## 4. 关键细节与注意事项

### 4.1 仓库与依赖管理

项目地址使用用户提供的 SSH remote。读取 GitHub 元数据不等于 SSH 可推送；实施时单独验证连接。阶段成果以独立提交/阶段分支提供审查，是否可推送以实际认证为准；认证失败时仍可交付本地文件和 diff，不伪称已上传。

第三方源代码放在忽略目录 `.external/opentelemetry-demo/`，通过固定提交获取，避免把整个 Demo 复制进项目或引入子模块管理成本。下载目录必须保持其上游结构，Compose 相对路径按第一个上游文件的目录解析。

本阶段 Python 探针使用标准库，不先创建 backend/frontend 骨架或添加应用依赖。Git 只提交本项目代码、覆盖配置、测试和脱敏文档。原始样本、渲染配置、本机环境文件、故障真值与本地论文先保持不跟踪；公开仓库中的交付报告只保留必要脱敏摘要。

### 4.2 部署形态与版本固定

使用 Docker Desktop 的 Linux 容器环境和 Compose。上游 minimal 组合为 `compose.yaml + compose.observability.yaml + compose.extras.yaml`，本项目最后叠加 `infra/otel-demo/compose.local.yaml`；不引入 full 或 agent 组合。

通过 `.env.override.example` 指定 `DEMO_VERSION=3.1.0`、`IMAGE_VERSION=3.1.0`，实施时复制为外部 Demo 目录内的本机 `.env.override`。分别核实源码提交、最终渲染镜像引用与拉取后的实际 digest；如固定 tag 镜像缺失，记录失败并报告，不静默改用 latest 或自行切换版本。

本机覆盖文件将需要访问的入口绑定至 loopback：

| 服务 | 初始宿主端点 | 用途 |
| --- | --- | --- |
| frontend-proxy | `127.0.0.1:8080` | 商店、Grafana、Jaeger UI/API、故障配置及负载界面 |
| prometheus | `127.0.0.1:9090` | 指标查询 |
| opensearch | `127.0.0.1:9200` | 日志 mapping/search |

同样清理其余不需要发布到宿主的端口，容器内部通信保持上游配置。覆盖采用 `ports: !override` / `!reset`，因此本阶段要求 Compose ≥2.24.4。渲染配置中核查实际监听地址和发布列表，避免追加端口后仍保留上游开放端口。端口冲突时调整本机覆盖和探针配置并记录，不能停止用户其他服务。

启动前检查可用磁盘，至少满足官方约 14 GB Demo 需求并留镜像/日志余量；实际运行观察内存、CPU 和磁盘增长，不把官方约 3 GB minimal 估算当成本机保证。只启动一个实验环境、采用低并发负载。若 OOM、镜像失败或持续不稳定，先定位原因；裁剪核心采集链路或迁移云端属于方案变更，需重新说明。

### 4.3 三类接口验证

**指标。** 使用 Prometheus HTTP query/query_range。先检查服务请求、错误、延迟，再核实 docker_stats 产生的 Ad CPU/内存序列、单位和容器归属。仅出现 `target_info` 或监控页面可打开，不足以通过。指标名以固定版实际响应为准，写入接入记录后冻结，不盲用旧名称；没有数据不补零。

**日志。** 查询 `otel-logs-*` 的 mapping 与指定窗 search，核实事件时间、观察时间、服务名、正文和严重度字段。至少取得 Payment 场景的实际日志。traceId/spanId 缺失时只记录服务/时间相关线索，不宣称与某条请求精确匹配。故障控制或注入标记的日志不进入后续盲诊断样本。

**链路。** 优先使用固定 Jaeger 版本的稳定 v3 HTTP API。默认候选路径为 `http://127.0.0.1:8080/jaeger/ui/api/v3/`，必须现场验证。按窗口查询后以 traceId 分组，再按 id 查询至少一条完整结账链，检查 `frontend→checkout→payment` 的可追溯父子关系。所有纳秒字段保持精度。合法 `No traces found` 结果、坏路由、后端不可用分别记录。v3 路径不通先核查代理和配置，不静默降级为内部 API；需要换协议时提交本阶段修订。

### 4.4 HTTP 探针的最小接口

计划入口：`python scripts/m0_probe.py --config configs/m0.local.json --start <UTC时间> --end <UTC时间> --output artifacts/m0/<run-id>`。以上为实施后的接口约定，本轮不创建脚本。

配置包含环境 id、三个 base URL、目标服务、已核实的指标表达式和容器映射；只允许本地 loopback HTTP 端点，拒绝任意外部地址和 URL 内嵌凭证。开始时间必须早于结束时间，单次窗口上限 15 分钟。配置格式使用 JSON，避免仅为探针引入 YAML 依赖。

探针只读取、检查和落盘，不启动服务、不启用故障、不修改后端数据。查询请求超时 10 秒、顺序执行、无自动重试；每次响应上限 10 MiB，日志先取最多 200 条，trace 搜索深度最多 100、按 id 保存最多 5 条，所有限制与截断写入报告。bounded 样本只用于验证接口，不用于准确率或延迟分布结论。

报告记录 schema_version、environment_id、window、captured_at、各检查的 pass/fail/needs_review、HTTP 状态、数量/字段摘要、失败原因及样本路径。HTTP 错误、空结果、JSON 格式错误、缺字段和截断必须区分。退出码 0 表示本次自动检查全部通过，1 表示检查失败或需要人工确认，2 表示参数/配置错误；0 不代表 M0 整体审查已经通过。

输出目录必须新建，已存在则拒绝覆盖。临时文件写完再改名；失败时保留明确失败记录，不以空 JSON 冒充有效响应。JSON 只作序列化，不使用 eval；查询参数用标准 URL 编码，不拼接 shell。

### 4.5 负载、故障与恢复

先验证健康状态，再逐个执行场景。每次先观察至少 10 分钟正常负载，通过官方故障 UI 操作并记录生效时间：

1. `paymentFailure`：使用该固定版定义的非零失败比例，发起真实结账；取得 Payment 错误日志、错误 spans 和错误率变化。若原始失败率或请求量不足以看出变化，先补足请求再复测，不把无样本判为成功。
2. 将该开关恢复至原值，确认新结账恢复成功、错误率回落，保留恢复后的新请求样本。
3. `adHighCpu`：开启并维持低并发首页流量，核实明确归属 Ad 的 CPU 序列变化；保存基线、故障、恢复窗的数值与配置。
4. 恢复 Ad 开关，再观察 CPU 回落及服务稳定性。对宿主机整体波动、错误容器映射或证据不足标记 needs_review，不宣称完成资源异常验证。

两个故障不重叠。完整正常→故障→恢复过程中，已启动组件应连续稳定运行至少 30 分钟并记录重启/OOM情况。关闭开关后检查实际恢复；故障状态未恢复或异常退出时优先恢复实验环境，并记录未完成项。

故障时间表和真实注入参数写入单独实验记录，不能直接交给未来诊断 worker。探针原始响应先保存为接入材料，M1 导入为盲输入前还需脱敏和排除泄漏字段。

### 4.6 测试、公开提交与环境限制

探针按 Python 常规编码约定组织：UTF-8、PEP 8 命名、清晰的小函数、主要输入输出加类型注解，命令行入口与可测试的查询/解析函数分开。保持一个脚本，测试导入时不发请求；错误日志输出到 stderr，不打印凭证或完整原始日志正文。配置通过 JSON 加载并校验，不为本阶段新增通用配置框架。

新增非平凡探针逻辑配套标准库 unittest：模拟 HTTP 成功、空结果、超时/错误、超大响应、非法 JSON、字段缺失、时间/地址校验和目录覆盖保护。fixtures 使用测试文件中的小型字典，不创建完整数据集。测试通过不替代本机集成验证。

仓库当前为公开仓库，原始 telemetry、浏览器会话信息、主机身份、凭证和未经检查的完整配置都不随 Git 提交。公开报告只含必要脱敏结果和校验摘要；原始接口样本保留本机供复核及下阶段使用。Demo 使用虚构业务数据也需检查额外采集的主机/环境属性。

若安装/切换组件需要重启、交互登录或影响当前其他服务，先说明具体影响并安排操作，不在未核实状态下修改系统配置。普通环境问题在 M0 内解决；确需改全局技术路线时先修订方案并增加架构影响评估。

## 7. 验收标准与交付审查

### 7.1 本阶段完成条件

| 检查项 | 通过条件 |
| --- | --- |
| 版本可复核 | 源提交、镜像实际 digest、渲染配置摘要与复现命令齐全；无浮动 latest |
| 环境稳定 | 连续至少 30 分钟负载/实验观察，核心服务无未解释重启或 OOM；记录实际资源占用 |
| 正常请求可追踪 | 至少一次真实成功结账及可解析的跨服务调用样本，服务身份可核对 |
| 指标可用 | 请求/错误/延迟有实际序列；Ad CPU 与内存可明确归属并核实单位 |
| 日志可用 | Payment 日志可按时间/服务查询，mapping 与关联字段覆盖已记录 |
| 链路可用 | 稳定 v3 查询可用，能按窗口搜索并按 id 取完整 trace，已知父子边可核对 |
| 故障与恢复 | Payment 错误场景和 Ad CPU 场景各完成一轮，并保存基线/故障/恢复数据；不把无数据当通过 |
| 探针正确 | 标准库测试通过，实际接口读取成功；错误、空结果、截断能区分，旧产物不被覆盖 |
| 文档与提交 | runbook 与实际命令一致；交付报告按条标明结果；Git 变更列表经核对不含私有数据 |

缺少任一必需数据、故障恢复或验证记录时，M0 标记未完成/部分完成，继续在本阶段修正；工具执行成功不能代替这些标准。DeepSeek、RCAEval、业务诊断效果不在本阶段通过条件内。

### 7.2 本次确认对象与后续流程

本方案的确认对象为上述 **M0 范围、约束、文件计划和验收标准**。全局路线认可不自动开启本阶段实施；本阶段已获单独确认，记录见下文。

设计获明确确认后，仅实施 M0；交付时提交文件/阶段差异、运行与测试记录、本机证据路径、公开脱敏报告和未解决事项，等待用户审查。不通过则在 M0 迭代。用户审查通过后只用一两句话指出原路线下一步方向，不在同一轮展开下一阶段方案；启动下一阶段需再次提交设计并等待确认。

确认记录：2026-11-16，用户明确“目前看基本没问题，开始实施吧”。开发状态：M0实现和限定验证完成。交付审查：已提交，等待用户审查，未进入M1。新增实施约束：代码规划与编辑结合 Ponytail，遵循最小完整实现和必要测试。

本阶段沿用既定全局架构，无新增全局架构变更；如实施发现必须调整，将先修订方案并新增“全局架构影响评估”。
